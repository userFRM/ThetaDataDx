# Working in this repository

This is the standing brief for anyone maintaining ThetaDataDx, human or agent. It is not a style
guide. It is the set of judgements that have already been made here, written down so they are not
relitigated, plus the working knowledge that is otherwise only recoverable by breaking something.

Read it before the first edit.

---

## 1. What this is

A market-data SDK for ThetaData. One Rust core, four language surfaces generated from it, two
binaries.

| Path | What it is |
| --- | --- |
| `thetadatadx-rs/` | The core. gRPC market-data client (MDDS), the streaming client (FPSS), decode, flat files, config, auth. Everything else is a projection of this. |
| `thetadatadx-ffi/` | The C ABI. `#[no_mangle] extern "C"` symbols the C++ SDK links against. |
| `thetadatadx-py/` | Python bindings (PyO3). Ships as `thetadatadx-py` on PyPI, imports as `thetadatadx`. |
| `thetadatadx-ts/` | TypeScript/Node bindings (napi-rs). |
| `thetadatadx-cpp/` | Header-and-source C++ SDK over the C ABI. CMake. |
| `tools/server/` | A drop-in replacement for the vendor's JVM terminal. Local-only: it binds a loopback port for the user's own tooling. |
| `tools/mcp/` | An MCP server. Holds live subscriptions and answers questions about them, plus history and flat-file tools. |
| `scripts/ci/` | The gate suite. One script per gate, dispatched by `scripts/ci.py`. |
| `docs-site/` | The published documentation. Its changelog is kept identical to `CHANGELOG.md`. |

**`thetadatadx-py`, `thetadatadx-ts`, `tools/mcp` and `tools/server` are excluded from the Cargo
workspace.** A workspace-wide `cargo test` does not touch them. This is the single most common way a
change reaches CI untested. Run them separately; see §4.

### The baseline

The vendor ships a terminal. **The terminal is the baseline.** Whatever it serves, this SDK serves,
byte for byte. Whatever it does not serve, this SDK does not invent.

The rule has two directions and they point opposite ways:

- **Data and semantics are a ceiling.** Which ticks, which columns, what values, what order: the
  terminal is the exact spec. Anything above it is invention. Delete it.
- **Engineering is a floor.** Transport, resilience, throughput, ergonomics: the terminal is a
  baseline, sometimes a lazy one, and beating it is the point. Raising an HTTP/2 window past the
  terminal's own cap is not a parity violation; it is the reason to exist.

Do not apply the data rule to an engineering decision. That leaves performance on the table to match
a number the vendor picked badly.

**Nothing derived that the vendor did not send.** No greeks computed here, no implied volatility, no
aggressor side, no bars built from trades. The vendor's own bar is served as it arrived. Where a
value is computed locally, the surface that exposes it says so.

The test for whether an accessor belongs: does it decode something the wire carried? A condition
code, a bit in a flag word, a volume type: yes. Arithmetic on a timestamp against constants chosen
here: no, however useful it looks.

## 2. Generated code and the single sources of truth

Most of the public surface is generated. The schema is the truth; the generated files are committed
so a consumer never needs the generator.

| Source | Drives |
| --- | --- |
| `thetadatadx-rs/tick_schema.toml` | Every tick struct, its columns, its byte layout, its flag accessors, across all four surfaces. |
| `thetadatadx-rs/endpoint_surface.toml` | The endpoint surface on every binding. |
| `thetadatadx-rs/sdk_surface.toml` | The non-endpoint SDK surface. |
| `thetadatadx-rs/config_surface.toml` | Config accessors for the FFI and C++. |
| `thetadatadx-rs/fpss_event_schema.toml` | Every streaming event. |
| `thetadatadx-rs/proto/mdds.proto` | The vendor's gRPC service. |
| `parity.toml` | The declared cross-binding surface the parity gate enforces. |

Regenerate with:

```sh
cargo run -p thetadatadx-rs --features config-file --bin generate_sdk_surfaces
```

Edit the schema, run that, commit both the schema and the regenerated files. The parity gate then
confirms every binding agrees.

**Never hand-edit a file whose header says `@generated`.** They live under `*/src/_generated/`, in
`thetadatadx-ffi/src/`, and as `thetadatadx-cpp/include/*.inc`.

`thetadatadx-ts/index.d.ts` and `index.js` are generated by the napi toolchain, not by
`generate_sdk_surfaces`, and **no gate in `ci.py all` rebuilds them.** A change to the Rust surface
can therefore leave the published TypeScript declaration advertising a field the binding no longer
exposes, with every local check green. Run `python3 scripts/dev/check_napi_drift.py` whenever a
change touches the TypeScript surface. It is deliberately not in `ci.py all` because it compiles the
crate.

## 3. The bar

**Build the complete thing.** Do not offer a minimal version and a proper version and ask which.
Build the one that holds. Scope can be cut; the primitive underneath it cannot.

**Lean on scope, maximal on quality.** Cut speculative features, abstractions with one caller, layers
nobody asked for, config for a value that never changes. None of that licenses a weaker
implementation. On a correctness or performance path, go the whole way to the right primitive even
when it costs a larger structural change. "Smallest diff" is never the argument for the weaker one.

**The smallest diff that is actually right.** Deleting beats adding. Abstraction threshold: one
caller, inline. Two callers, inline. Three with real variation, maybe a helper. A trait only when
runtime polymorphism is genuinely needed. If the answer is eight lines, it is eight lines.

**Fix the cause, not the symptom.** A report names a symptom. Before editing, find every caller of
the function you are about to touch. One guard in the shared path is a smaller diff than a guard in
every caller, and patching only the path the report names leaves every sibling broken.

**No dead code.** Not commented out, not behind a flag nobody sets, not kept because it might be
useful. No `#[allow(dead_code)]`, no `#[allow(unused)]`, no `|| true` in a script, ever. If the
compiler says it is unused, delete it or fix the logic so it is used. Generated code that warns is
generated code that is wrong: fix the generator, never silence the lint.

**Names say what a thing is.** `Cache` for read-mostly time-bounded storage, `Service` for something
that does work, and `Snapshot`, `Tick`, `Bar`, `Quote`, `Trade`, `Subscription`, `Feed`, `Stream`,
`Spec`, `Filter` for what they say. Never `Manager`, `Helper`, `Handler`, `Util`, `Oracle`, nor
anything cute. A name that needs the surrounding code to make sense is the wrong name. Renaming is a
separate decision from whatever you came to do: propose it, do not fold it in.

**Contracts are identified financially.** A root for a stock, index or ETF; root plus expiration plus
right plus strike for an option. The vendor's internal contract id is a session-scoped routing key
that drifts within a day. It is engine-internal and never an input on a public surface.

**One polymorphic method, not parallel methods per input shape.** `for_contracts` taking anything
that converts into the target, not `for_roots` beside `for_options`.

**Integer milliseconds or microseconds on every hot path.** Never a datetime type inside a per-tick
loop; convert once at a display or API boundary. An integer compare is about a nanosecond,
constructing a datetime is hundreds plus an allocation.

**Never hold the Python GIL on a blocking path.** Either the async surface driven by descriptor
readiness with no polling, or release the lock explicitly around the block. Build Python objects only
after the lock is back.

**Handlers and drains on a delivery surface, never a channel receiver.** A queue has one reader,
drops under load, and copies every event. If you are adding a "how many did we lose" counter to a
delivery queue, the shape is wrong.

## 4. Commands

Prerequisites: a Rust toolchain at or above the `rust-version` in `thetadatadx-rs/Cargo.toml`,
Python 3.12+, Node with npm, CMake for the C++ SDK, and `maturin` to build the Python
extension. `just` is the task runner the recipes are written for; without it, call the scripts
directly as shown.

### The gate suite

```sh
python3 scripts/ci.py all            # everything   (just ci)
python3 scripts/ci.py binding_parity # one gate      (just check binding_parity)
python3 scripts/ci.py list           # the gate names
```

`scripts/ci.py` is a thin dispatcher over the scripts in `scripts/ci/`. It reimplements no gate
logic, so running a gate script directly is equivalent.

Four gates need built artefacts and **fail on a clean checkout even with no changes**:
`c_abi_completeness`, `bench_regression`, `perf_gate`, `agreement`. Before treating any of them as
your failure, confirm it fails the same way on the base commit. That is the single most common false
alarm here.

Three of them pass once their artefact exists, and the whole suite then comes back clean:

```sh
cargo build -p thetadatadx-ffi --release                                        # c_abi_completeness
cargo bench -p thetadatadx-rs --features __internal --bench bench_decode_allocations  # perf_gate
cargo bench -p thetadatadx-rs --bench streaming_channels                        # bench_regression
```

`perf_gate` compares allocations per decoded row against a committed baseline, so it is deterministic
and a rise is a real regression. `bench_regression` compares wall-clock times on whatever machine ran
them, so a local delta inside the threshold says little and one outside it is worth a second run
before believing.

### Tests, per surface

```sh
cargo test -p thetadatadx-rs                   # the core
cargo test -p thetadatadx-ffi                  # the C ABI
(cd tools/mcp && cargo test)                   # workspace-EXCLUDED
(cd tools/server && cargo test)                # workspace-EXCLUDED
(cd thetadatadx-ts && npm ci && npm test)      # workspace-EXCLUDED
maturin develop -m thetadatadx-py/Cargo.toml   # workspace-EXCLUDED; needs an active virtualenv
python -m pytest thetadatadx-py/tests -q
```

`maturin develop` needs `VIRTUAL_ENV` set or a `.venv` in a parent directory, and **the Python
extension must be rebuilt before pytest** or the suite tests the previous build.

### Lint

```sh
cargo clippy --all-targets -- -D warnings      # and again inside each excluded crate
cargo fmt --all
```

### Generators and drift

```sh
cargo run -p thetadatadx-rs --features config-file --bin generate_sdk_surfaces
python3 scripts/dev/check_napi_drift.py        # rebuilds napi and diffs the committed output
```

### Live checks

These reach the vendor's production systems and need credentials.

```sh
python3 scripts/dev/live_smoke.py creds.txt    # core, server and MCP against production
python3 scripts/dev/streaming_smoke.py         # takes optional --symbol / --option-symbol
python3 scripts/dev/streaming_soak.py
```

`just smoke creds.txt` runs the first two.

## 5. Reading before writing

Understand the problem fully, then be lazy. A small diff in the wrong place is not laziness, it is a
second bug wearing the costume of efficiency.

The most productive question to ask of any line is whether it can fail.

**A check that cannot fail is not a check**, and it is worse than none, because it is believed. A
condition that is always true. A test that would still pass with the logic under it deleted. A guard
on a state the code cannot reach. An assertion comparing a value to itself, or a constant to the same
constant. This applies to tests as hard as to production code.

Two specific shapes worth naming:

- **A skip that excuses itself on silence.** Silence is where "we asked wrongly" and "there was
  nothing to say" look identical, and the second reading is always the one that keeps the suite
  green. Make every skip name its evidence.
- **A guard keyed to a literal phrase rather than the property.** It blocks correct rewrites now, and
  the moment the wording changes it stops testing anything at all, silently.

A guard must name the thing it guards rather than depend on running first. If a change is mostly
repairing the guards from the previous change, stop patching and do the design.

Four traps that have each cost real time here:

- **Before moving code earlier in a function**, read every rebinding between the old site and the new
  one. A moved construction reads the value from before the shadow.
- **Before inserting an item above another**, anchor on the previous item's closing brace or on the
  first line of the next item's doc block. Never on its declaration line, or the new item silently
  takes the doc comment and the item below is left bare. Both still compile.
- **Before defaulting an unreadable wire field**, ask whether any later read depends on its value: a
  count, a length, a width flag, a presence bit. If so, refuse the whole payload. A default there
  desyncs the cursor and the overrun guard cannot fire, so the result arrives complete, plausible and
  fabricated.
- **Instrument before theorising.** One log line beats three confident root causes.

## 6. Verification

**Prove a non-trivial fix by breaking it.** Change the production path so the defect returns, watch
the named test fail, restore the file and confirm it is byte-identical. A fix without that is a fix
you hope works.

Three ways this proves nothing, all worth checking for:

- It did not compile, usually on a now-unused binding under `-D warnings`. Nothing ran. Keep the
  binding live.
- It did not apply, because the formatter moved the line it anchored on. Assert the anchor exists
  before replacing it.
- It was equivalent and changed nothing observable. Then the test is not discriminating, and the test
  is what needs work.

Restore from a copy taken beforehand. Never use version control to undo it: that reverts everything
else in the file too.

**Run the full gate locally before pushing**, including the excluded crates.

**Never push in the same command as the gate.** The push runs whether the gate passed or not.

**Check CI after every push.** Not the next morning.

**Empty output is a failure, not a pass.** A count captured into a shell variable can leave the file
empty while the count reads zero; a run filtered down to no tests exits 0. If a check prints nothing,
find out whether it ran.

## 7. The public record

Commits, pull requests, issues, review comments, the changelog and the release notes are all read by
users. They describe the software, not the work.

State the defect and the reasoning. Never the process: no round numbers, no finding counts, no review
or audit vocabulary, no narration of how the change was arrived at, no mention of the tools used to
produce it. A reader in two years wants to know what was wrong and why the fix is correct. Everything
else is noise in the permanent record.

Conventional Commits. The subject says what changed; the body says why it was wrong before.

Changelog entries describe what a user can now do, or no longer has to work around, in prose, with
the reason it was wrong before. They are not commit summaries. `CHANGELOG.md` and
`docs-site/docs/changelog.md` stay identical below the title.

Issues are Problem, Solution, Impact. Check the open ones first, including your own.

Prose does not hard-wrap. Write paragraphs and let the renderer wrap them.

Never published, in any of the above:

- **Fabricated numbers.** Every published figure has a committed builder anyone can re-run. A number
  that cannot be reproduced on demand does not go in a changelog, a README or a PR body.
- **Claims a client-side measurement cannot support.** A number measured on one machine against one
  account is a number measured on one machine against one account.
- **Competitor names**, self-grading, or readiness claims.
- **Credentials, account identifiers, hostnames or addresses**, in code, docs, issues or fixtures.
- **Internal module paths and runtime details** in customer-facing documentation. The vendor's own
  protocol names are kept, deliberately, because staying aligned with the vendor's vocabulary is the
  point; our implementation's names are not. Public API names are fine. Contributor documents like
  this one are the exception.

Write in a plain voice. No em-dashes, no marketing cadence.

### Git

No force pushes. To undo your own unpushed mistake, reset; to undo something already shared, revert.

## 8. Streaming

The live surfaces carry the subtlest constraints in the repository. These are facts, not opinions.

**Tick shapes differ by transport.** The streaming trade tick and the request-response trade tick are
not the same shape and never have been. Conflating them produces code that looks right and decodes
garbage. Check the schema, not your memory.

**Not every asset class has every stream.** An index has no quote stream and no whole-market stream;
its price arrives on the trade subscription. Open interest counts option contracts outstanding and a
stock does not have one. Offering a subscription the vendor does not publish opens a book that stays
silent for ever.

**The whole-market trade stream wraps each print.** The quote that stood before it, the vendor's bar,
and the quotes after it arrive as separate messages around the trade. Correlating them is the
consumer's job, and the correlation must not span an interval nobody observed.

**Rates are far higher than a mean suggests.** A per-second average hides the burst that overflows the
buffer. At a market open the whole-market stock stream has been measured at roughly forty times the
mean of the minute containing it. Anything sized in rows states what it costs in memory and never
promises a length of time.

**The development cluster replays faster than real time.** Never size anything against numbers taken
from it.

**The idle wait is a deliberate choice.** The streaming consumer defaults to a spin wait, which holds
a full core for as long as the stream is connected. That is correct for a colocated consumer chasing
microseconds and wrong for anything running beside an editor, so tools that answer a question every
few seconds set a backing-off wait instead. Do not change that back without measuring the cost.

**Nothing in the ingest path allocates or takes a second lock.** It runs per message, at rates where
that matters.

**A subscription is scoped to the account, not to the connection.** Stopping one from here can stop a
stream a completely separate process on the same account was relying on. Treat any subscription
teardown as visible outside this program.

### Telling a caller what you do not know

The live surfaces exist to answer questions that cannot be answered by reading a feed directly. That
only works if every answer is honest about its own limits.

- An age describes the rows returned, not the newest thing on the feed.
- A window's stated bounds contain the rows it came back with.
- A count says which population it covers.
- A completeness claim is wrong in both directions. Reporting missing data that is present costs
  trust; reporting complete data that is not costs more.
- A timestamp the clock could not produce has no age at all, rather than one measured from the epoch.
- A request the server cannot honour is refused by name. It is never silently answered as a
  different, wider request: dropping a filter that failed to parse returns everything and says
  nothing.
- A read settles only once its answer is going to reach the caller. A call that fails leaves its
  rows, cursors and disclosures for the next one.

## 9. Acting on a review

Findings are not a to-do list. Reproduce each one in the code before acting on it, and reject the
ones that do not hold, with the reason. A reviewer reasoning by analogy from a real defect will
produce a plausible one that is not there, and a fix for a defect that does not exist is a new defect
with a test that locks it in.

Reject in particular anything that trades a real cost for a hypothetical one. A guard that discards
live data to close a race nobody can reach is not an improvement. `tools/server` binds a loopback
port for the machine's own user, so hardening it against hostile traffic is scope, not safety.

When two independent reviewers land on the same point, look again at it even if you dismissed it the
first time.

## 10. Not done without asking

- Renaming anything on a public surface.
- Anything destructive: force pushes, history rewrites, removing files or directories outside the
  change that was asked for.
- Pointing undocumented calls at the vendor's production systems, including read-only probes. The
  vendor's operational services in particular carry mutating calls beside the read ones; those are
  never called against a live service whatever is decided about reachability.
- Publishing, releasing or tagging. A release runs the workflow as it exists **at the tag**, so any
  fix to the release pipeline has to land before the tag, not after.

When a request is ambiguous in a way that changes the work, ask once and then commit. When it is not,
do the whole thing rather than half of it and a question.
